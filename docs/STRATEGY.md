## 1. Проблема и цель

### 1.1. Проблема

События компании и страны (праздники Грузии, маркетинговые/сезонные поводы, дни рождения сотрудников) сейчас лежат в разрозненных файлах (Excel + переписка в Telegram). Нет единого места, где:

1. удобно **хранить и править** даты;
2. система **напоминает заранее**, чтобы маркетинг успел подготовить акции и ивенты;
3. HR/команда **не забывает** дни рождения.

### 1.2. Цель продукта

Построить систему «календарь событий DimKava», которая:

- хранит события в **Jira** (отдельный project `DEC`);
- шлёт оповещения в **Telegram**;
- различает **праздники/промо-поводы** и **дни рождения** (разные окна напоминаний и разный смысл карточек).

### 1.3. Не-цели (вне scope v1)

- Полноценный UI «как Google Calendar» (календарная сетка, drag-and-drop).
- Публичный сайт-календарь для гостей.
- Автоматический расчёт всех подвижных дат (Пасха, Тбилисоба и т.д.) без ручного ввода.
- Замена HRIS / кадровой системы.
- Миграция задач из project `DG` в `DEC` (это разные контуры).

## 2. Глоссарий

| Термин | Значение |
|--------|----------|
| **SSOT** | Single Source of Truth — единственное место, где правят «правду» о событии |
| **Праздник / промо-повод** | Событие, под которое готовят **акции и ивенты** (госпраздник, кофе-день, сезон, коммерция, DK-событие) |
| **День рождения (ДР)** | День рождения сотрудника; нужна только памятка поздравить |
| **T−N** | Напоминание за N календарных дней до даты события (`duedate`) |
| **T−0** | День самого события |
| **DEC** | Jira project key: **D**imKava **E**vent **C**alendar |
| **DG** | Существующий Jira project рабочих задач DimKava Georgia (`dimkavageorgia.atlassian.net`) — **не** использовать как календарь |
| **Idempotent alert** | Одно и то же окно `(issue_key, window)` отправляется не больше одного раза |
| **Подвижная дата** | Дата меняется год от года (Пасха, Тбилисоба, Black Friday «конец ноября» и т.п.) |

## 5. Best practices (контекст) и сознательный выбор DimKava

В индустрии часто SSOT — таблица/календарь, а Jira — только work items.  
**Заказчик сознательно выбрал иначе:** удобство команды DimKava — **вести и править в Jira**, **слышать в Telegram**.

Это валидный ops-выбор при условиях:

- отдельный project (`DEC`), чтобы не засорять `DG`;
- чёткие labels / типы;
- идемпотентные алерты;
- понятные шаблоны description.

Другие практики, которые **сохраняем**:

- таксономия (праздник ≠ ДР);
- один timezone;
- окна напоминаний с дедупом;
- владелец данных (маркетинг vs HR) — см. открытые вопросы.

### 6.1. Модель issue в Jira

Рекомендуемая минимальная модель v1 (без обязательных custom fields; можно позже добавить):

| Аспект | Правило |
|--------|---------|
| Issue type | Обычный `Task` (или один dedicated type, если создадут в DEC) |
| Summary | Человекочитаемое имя события, напр. `[Праздник] Начало учебного года` / `[ДР] Аня Батуми` |
| `duedate` | Дата события (для ДР — дата **в текущем/следующем** году, см. §6.3) |
| Labels (обязательно одно из) | `calendar-holiday` **или** `calendar-promo` **или** `calendar-birthday` |
| Доп. labels (опционально) | `georgia`, `coffee`, `seasonal`, `commercial`, `dk-internal`, `pilot-test` |
| Description | Для holiday/promo: краткое описание + чеклист подготовки акции; для birthday: ФИО/точка, MM-DD |
| Assignee | Открытый вопрос (см. §11); для пилота можно оставить Unassigned + watchers |

**Маппинг типов Excel → labels (рекомендация):**

| Тип в Excel / смысл | Label |
|---------------------|-------|
| Грузия, гос/религия | `calendar-holiday` |
| Сезонный, Кофе, Международный, Коммерческий, DK / … | `calendar-promo` (или `calendar-holiday`, если это именно выходной/праздник страны — на усмотрение при импорте; главное — **не** `calendar-birthday`) |
| ДР сотрудника | `calendar-birthday` |

Правило напоминаний смотрит **только на label семьи** (`birthday` vs всё остальное), не на Excel-тип.

### 6.2. Правила окон напоминаний

Пусть `D = duedate` (дата в timezone `Asia/Tbilisi`), `today` — локальная дата в том же TZ.  
`days = (D - today).days`.

**Если label = `calendar-birthday`:**

| Условие | Window id | Действие |
|---------|-----------|----------|
| `today == D - 1 day` | `t_minus_1` | TG: «Завтра день рождения: …» |
| `today == D` | `t_minus_0` | TG: «Сегодня день рождения: …» |

Без workflow-пингов.

**Если label ∈ {`calendar-holiday`, `calendar-promo`}:**

| Условие | Window id | Действие |
|---------|-----------|----------|
| `today == D - 30` | `t_minus_30` | Одноразовый TG + comment |
| `today == D - 15` | `t_minus_15` | Одноразовый TG + comment |
| `1 <= days <= 30` и статус **К выполнению** (`statusCategory=new`) | `nag_start_work_morning` / `nag_start_work_evening` | TG в **10:00** и **22:00**, пока не перенесут в **В работе** |
| `1 <= days <= 5` и статус не Готово | `nag_finish_done_morning` | TG в **10:00**: доведите до **Готово** |

**Не слать** birthday-окна для holiday и наоборот.

**Идемпотентность:**  
- one-shot: `(issue_key, window, duedate)`  
- nags: `(issue_key, window, duedate, today)` — можно снова на следующий день / другой слот.  
Локальный store + comment в Jira.

### 6.3. Дни рождения и год

В источнике только MM-DD. В Jira `duedate` требует полный ISO date.

**Правило v1 (рекомендация):**

- При импорте/ежегодном rollover ставить `duedate = ближайшая ещё не прошедшая дата MM-DD в году today.year` (если уже прошло — `today.year + 1`).
- После прохождения даты — job или ручной скрипт **+1 год** к `duedate`.
- В description хранить канонический `birthday_mmdd: MM-DD` и имя.

Открытый вопрос заказчику: подтвердить «один issue на человека навсегда» (§11).

### 6.4. Подвижные и размытые даты

Строки вроде «Подвижная дата», «Конец ноября», «Последняя неделя декабря», «Середина января»:

- **Не** ставить фейковый `duedate` без решения человека.
- Импортировать как issue **без** `duedate` **или** с label `needs-date` и не включать в alert job, пока дата не проставлена.
- После уточнения даты человеком в Jira — попадают в обычный контур.

### 6.5. Daily job (два слота)

- Расписание `Asia/Tbilisi`: **10:00** (`--slot morning` или `auto`) и **22:00** (`--slot evening` / `auto`).
- Host: Windows Task Scheduler или Railway cron (два trigger’а).
- Алгоритм:
  1. JQL: `project = DEC AND labels in (…) AND duedate is not EMPTY AND statusCategory != Done`
  2. Для каждой issue: one-shot окна + workflow nags по статусу и `--slot`
  3. Идемпотентная отправка TG + comment
  4. Ошибка TG → не помечать sent

```powershell
python -m dec_calendar run-once --slot morning
python -m dec_calendar run-once --slot evening
```

## 12. Acceptance criteria (когда считать MVP успешным)

1. В Jira существует project `DEC` с импортированными событиями из Excel (датированные) и ДР из файла Нини.

5. Реальная отправка: пока `NOTIFY_VIA_HUB=false` — `@prices_monitoring_alerts_bot`; цель — `@dimkava_public_alerts_bot` через Notify Hub (канал `public`).

7. Изменение `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` в env меняет получателя без правки кода.
8. Документация в README: как добавить событие и как запускать job.
